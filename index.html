Making websites and apps, explained simply

Every website is built from layers. Each topic below climbs four levels, from a plain-words explanation to expert detail, so you can stop wherever you like.

Simple explanationTechnical detailDeep diveExpert level

The page you see

  • HTML and CSS

    HTML decides what is on the page: headings, text, images, buttons. CSS decides how it looks: colors, fonts, spacing, and how it adapts to a phone.

    In simple words: HTML is the walls and rooms of a house. CSS is the paint and furniture.

    Deep dive: Semantic HTML (header, nav, main, article) gives screen readers and search engines real structure and is the foundation of accessibility (WCAG). In CSS I work with the cascade and specificity deliberately, use custom properties as design tokens, Flexbox for one-dimensional layout, Grid for two-dimensional layout, container queries, and fluid type with clamp(). I animate only transform and opacity to keep the GPU doing the work, and budget Core Web Vitals (LCP, INP, CLS) from the first day.

    Expert: Critical rendering path: HTML builds the DOM, CSS builds the CSSOM, and together they form the render tree. I inline critical CSS, defer scripts, preload key fonts, serve responsive images in AVIF or WebP, and avoid layout thrash by batching DOM reads and writes. Targets: LCP under 2.5 s, INP under 200 ms, CLS under 0.1.

  • JavaScript

    The language that makes pages react: menus that open, forms that check themselves, animations, live updates without reloading.

    In simple words: It’s the electricity. Without it the house looks nice but nothing turns on.

    Deep dive: JavaScript runs on one thread with an event loop: synchronous code finishes first, then microtasks (Promises), then timers and I/O callbacks. I use closures and ES modules for encapsulation, async/await with proper error handling, AbortController to cancel requests, debouncing for noisy events, and Web Workers when heavy computation would otherwise block the interface.

    Expert: Engines such as V8 compile hot functions to machine code and rely on stable object shapes, so I keep objects uniform. I avoid memory leaks from forgotten listeners and closures, use structured clone and transferable objects with Workers, and rely on TypeScript strict mode to remove whole classes of runtime errors.

  • React

    A tool for building large interfaces from small reusable pieces. Fast to update, easy to grow, and the standard for modern web apps.

    In simple words: Like LEGO. Build a button once, use it a hundred times, and fix it everywhere in one go.

    Deep dive: When state changes React re-renders, reconciles the new virtual tree against the old one, and patches only the differences. I control render cost with stable keys, state kept as local as possible, memoization where it is measured to help, code splitting with lazy loading, and transitions for responsive updates. For 3D I drive Three.js declaratively through React Three Fiber.

    Expert: I treat renders as pure functions, lift or colocate state deliberately, use useMemo and useCallback only where profiling proves a gain, virtualise long lists, stream server-rendered HTML with Suspense and hydrate selectively. Effects are for synchronising with the outside world, never for deriving data.

  • Node.js and PHP

    The server side: code that runs out of sight, handles logins, payments and orders, and talks to the database. Node.js is great for realtime apps; PHP powers a huge part of the web, including many business sites.

    In simple words: The kitchen of a restaurant. You never see it, but it prepares everything you ordered.

    Deep dive: Node.js uses non-blocking I/O on the libuv event loop, ideal for APIs and realtime sockets, while CPU-heavy work moves to worker threads or queues. In Express I layer middleware: logging, rate limiting, authentication, validation, then handlers. PHP runs per request behind Nginx and PHP-FPM; I use PDO prepared statements, password_hash with Argon2, CSRF tokens, strict session cookies (HttpOnly, Secure, SameSite) and Composer for dependencies. Both sit behind a reverse proxy with TLS.

    Expert: In Node I watch event-loop lag, never block it with synchronous work, use streams with back-pressure for large payloads, scale horizontally and shut down gracefully on SIGTERM. In PHP I enable OPcache and preloading, use strict types, and isolate pools per site in PHP-FPM.

  • Forms and user input

    Forms are how visitors talk to a site: signing up, searching, paying. A good form labels every field, checks the answer, and tells the person clearly what went wrong.

    In simple words: A paper form with clear boxes and a helpful clerk who points at the exact mistake.

    Deep dive: I use real label elements, input types (email, tel, number) that bring the right phone keyboard, and the built-in validation attributes, then add custom messages with aria-live so screen readers hear them. Buttons disable while sending to prevent double submits.

    Expert: Client checks are only convenience; the server must validate everything again because anyone can bypass the browser. I preserve typed values on error, debounce async checks, support autofill and password managers, and guard against CSRF and bots with tokens and rate limits.

  • State and loading screens

    A page is never just ‘finished’. It is loading, empty, showing data, or broken, and each of these states needs its own design.

    In simple words: A shop window: a ‘back in 5 minutes’ sign is better than a blank glass.

    Deep dive: State is the data a screen remembers: the typed text, the open menu, the fetched list. I keep it as local as possible, fetch data with loading and error branches, and show skeleton placeholders so the layout does not jump.

    Expert: I separate server state (cached, shared, can go stale) from UI state, using a query library for caching, retries and background refresh. Optimistic updates make actions feel instant and roll back on failure, and every request can be cancelled when the user navigates away.

  • Components and props

    A component is a reusable piece of screen: a button, a card, a whole page. Props are the settings you hand it, like a title or a color.

    In simple words: A cookie cutter: one shape, many cookies, each with its own icing.

    Deep dive: I keep components small with one job, pass data down as props and send events up as callback functions. Shared pieces live in a design system so spacing, colors and behaviour stay consistent everywhere.

    Expert: I prefer composition over inheritance, avoid prop drilling with context only for truly global data, and keep components pure so they are easy to test and memoize. Props are typed with TypeScript and documented in Storybook.

  • Routing in single-page apps

    In a single-page app the browser loads once and JavaScript swaps the screen when the address changes, so moving around feels instant.

    In simple words: Changing the scenery on a stage instead of rebuilding the whole theatre.

    Deep dive: A router maps URL patterns to components, including dynamic parts like /users/42. It uses the History API, so back and forward buttons work, and lazy-loads each route so the first visit stays small.

    Expert: Private routes redirect before rendering, scroll and focus are restored on navigation so keyboard users are not lost, and server rendering gives crawlers and slow phones real HTML. A 404 route and sensible error boundaries catch the rest.

  • Fetching data and CORS

    The browser asks an API for data with fetch and shows the answer. Browsers also block one site from reading another’s data unless that server clearly allows it.

    In simple words: Calling a company: the receptionist only connects you if your name is on the approved list.

    Deep dive: fetch returns a Promise; I check response.ok, parse JSON, handle network failure and use AbortController for timeouts. CORS is controlled by server headers such as Access-Control-Allow-Origin, and a preflight OPTIONS request checks risky calls first.

    Expert: I allow only named origins, never a wildcard with credentials, and keep tokens out of localStorage where XSS can read them. Requests are retried with back-off, deduplicated and cached so a fast-clicking user does not flood the API.

  • Modern CSS and design tokens

    Today’s CSS can do what once needed scripts: variables, dark mode, fluid sizes and layouts that adapt to the space they sit in.

    In simple words: A paint chart: choose the colors once, then every room uses the same names.

    Deep dive: I define custom properties like --gold on :root, switch them inside prefers-color-scheme, and use clamp() for fluid text. Container queries let a card change layout by its own width, not the whole screen’s.

    Expert: I use logical properties (margin-inline) so right-to-left languages work automatically, :has() for parent-aware styling, cascade layers to tame specificity, and utility frameworks like Tailwind only when the team agrees on the token scale. Unused CSS is purged at build time.

  • Animation, canvas and 3D

    Motion guides the eye and explains change. CSS handles simple effects; JavaScript, canvas and WebGL handle games, charts and 3D scenes like the one behind this page.

    In simple words: A flip-book: many still pictures shown fast enough to look alive.

    Deep dive: CSS transitions and keyframes animate transform and opacity on the GPU. For custom drawing I call requestAnimationFrame so the browser paints once per screen refresh, and Three.js wraps WebGL with scenes, cameras and lights.

    Expert: Frames get 16 ms at 60 Hz, so I pause off-screen animation, cap pixel ratio on weak devices, reuse geometry, and respect prefers-reduced-motion by replacing movement with a still view. Animation must never be the only way to understand content.

  • Offline apps and browser storage

    A site can keep data in the browser and even work without internet. Such apps are called progressive web apps, and they can be installed like a phone app.

    In simple words: A picnic basket: pack the essentials before you leave, so a lost signal does not ruin the day.

    Deep dive: A service worker sits between the page and the network and answers from a cache when offline. localStorage holds small strings, while IndexedDB stores larger structured data, and a manifest file makes the app installable.

    Expert: I choose cache strategies per resource: cache-first for fonts and images, network-first for data, stale-while-revalidate for the middle. Versioned caches are cleaned on update, and nothing sensitive goes in storage that a script injected through XSS could read.

How pages travel and render

Servers, APIs and data

  • APIs and HTTP

    An API is a menu of requests one program can send to another. Web APIs use HTTP: a method such as GET or POST, a path, headers and a body, answered by a status code and data, usually JSON.

    In simple words: A waiter between the dining room and the kitchen: you order from the menu and never walk into the kitchen yourself.

    Deep dive: I design REST resources with consistent naming, correct status codes, pagination, idempotent PUT and DELETE, versioning and clear error bodies. Authentication uses short-lived tokens, input is validated against a schema, and every endpoint is rate limited.

    Expert: For realtime I use WebSockets or server-sent events, for efficiency HTTP/2 multiplexing and caching headers (ETag, Cache-Control), and idempotency keys so payments can be retried safely. Contracts are written in OpenAPI so clients and tests are generated from one source of truth.

    REST · JSON · OpenAPI · WebSocket · HTTP/2

  • Databases

    A database stores information so it survives restarts and can be searched fast. SQL databases such as PostgreSQL and MySQL keep data in related tables with strict rules.

    In simple words: A giant, perfectly organised filing cabinet with a very fast librarian.

    Deep dive: I model data with normalisation, primary and foreign keys, and indexes chosen from real query plans (EXPLAIN). Transactions group changes so they succeed or fail together, following the ACID guarantees.

    Expert: I tune isolation levels against anomalies such as dirty and phantom reads, use connection pooling, partial and covering indexes, zero-downtime migrations, and replication with tested point-in-time recovery. Queries are always parameterised.

    PostgreSQL · MySQL · Redis · transactions · indexing

  • Sessions and cookies

    HTTP forgets you after every request. A session is how the server remembers you are logged in: it gives your browser a small cookie that proves who you are.

    In simple words: A coat-check ticket: hand it over and they know which coat is yours, without asking your name again.

    Deep dive: After login the server stores session data and sends a random ID in a cookie marked HttpOnly, Secure and SameSite. Sessions expire, logging out destroys them, and the ID is regenerated after login to stop fixation.

    Expert: Server-side sessions can be revoked instantly; stateless JWTs scale easily but are hard to cancel, so I keep them short-lived with refresh tokens. I store sessions in Redis, bind them to risk signals, and never put secrets or permissions in client-readable data.

  • Validation and error handling

    Servers must expect bad input and unexpected failures. Good back-end code checks every request and answers errors with a clear status and a safe message.

    In simple words: An airport check-in: wrong passport gets a clear explanation, not a crash of the whole airport.

    Deep dive: I validate type, length, range and format against a schema, return 400 for bad input and 404 or 409 where they fit, and wrap handlers in a central error middleware so one mistake never crashes the process.

    Expert: Users see friendly messages while the real stack trace goes to logs with a request ID, so leaks of internals are impossible. I treat all input as hostile, set body size limits and timeouts, and make failures retryable with idempotency keys.

  • Login with OAuth and roles

    ‘Sign in with Google’ is OAuth. Authentication proves who you are; authorization decides what you may do, often through roles such as user and admin.

    In simple words: A hotel: the front desk checks your ID once, then your key card opens only your room.

    Deep dive: The app redirects to the provider, gets a one-time code back, and swaps it on the server for tokens. I check permissions on every request with role-based access control, never only by hiding buttons in the interface.

    Expert: I use the authorization-code flow with PKCE, validate state and redirect URIs, request minimal scopes and verify token signature, issuer, audience and expiry. Broken access control, such as changing an ID in the URL, is the top web risk, so every object lookup checks ownership.

  • Layers, ORMs and migrations

    Back-end code works best split into layers: routes receive requests, services hold the rules, and a data layer talks to the database. An ORM lets you use database rows as ordinary objects.

    In simple words: A restaurant: waiters take orders, chefs follow recipes, and the storeroom keeper handles the ingredients.

    Deep dive: Tools like Prisma, Sequelize or Eloquent build safe parameterised queries. A migration is a versioned file that changes the schema, so every developer and server gets the same database structure in the same order.

    Expert: I watch for the N+1 query problem, add indexes from real query plans, and run risky migrations in two safe steps (add, backfill, then remove) so deploys cause no downtime. Business rules stay out of controllers so they can be tested without HTTP.

  • File uploads and storage

    Letting people upload files is one of the riskiest features, because a file can be disguised. The server must check what it really is before keeping it.

    In simple words: A mailroom that opens and checks every parcel before putting it on the shelf.

    Deep dive: I limit size and count, check the real type from the file’s content rather than its name, generate a random filename, and store files outside the web root or in object storage such as S3 so they can never run as code.

    Expert: Large files go straight from the browser to storage through short-lived signed URLs, so they never load the app server. I scan for malware, strip image metadata, re-encode images to destroy hidden payloads, and serve downloads with a safe Content-Type and Content-Disposition.

  • Realtime with WebSockets

    Normal web requests only answer when asked. A WebSocket stays open, so the server can send news the moment it happens.

    In simple words: A phone call instead of sending letters: both sides talk whenever they like.

    Deep dive: The connection starts as HTTP and upgrades. I use Socket.IO or the ws library on Node, group clients into rooms, send small JSON messages and add heartbeats to detect dead connections. Server-sent events suit one-way feeds more simply.

    Expert: Sockets are stateful, so scaling needs a shared pub/sub layer such as Redis so every server can reach every client. I authenticate during the handshake, validate each message, rate limit senders, reconnect with back-off and resend missed messages by sequence number.

  • REST versus GraphQL

    REST gives each thing its own address. GraphQL has one address, and the client writes a query asking for exactly the fields it needs.

    In simple words: A set menu versus ordering exactly what you want from a list.

    Deep dive: REST is simple, cacheable and well understood. GraphQL avoids over-fetching and many round trips, which suits mobile apps, but needs a schema, resolvers and care so one query cannot be too expensive.

    Expert: I limit query depth and cost, batch database calls with a data loader to avoid N+1, disable introspection in production when appropriate, and use persisted queries. HTTP caching is harder in GraphQL, so I cache at the resolver or CDN-by-query level.

  • API testing and documentation

    An API is a promise to other developers. Tests prove the promise holds, and documentation tells people how to use it without asking you.

    In simple words: A product manual and a quality check on the factory line.

    Deep dive: I write integration tests that call real endpoints against a test database with Supertest or pytest, check status codes, bodies and error cases, and describe the API in an OpenAPI file that renders interactive docs in Swagger UI.

    Expert: Contract tests catch breaking changes before clients do, load tests (k6, Locust) find the point where latency climbs, and security tests try missing tokens, other users’ IDs and oversized payloads. Deprecations are announced with versioning and Sunset headers.

Shipping it

  • Git and delivery

    Git records every change to the code so work can be reviewed, undone and shared. Continuous integration runs tests automatically on every change, and continuous deployment ships the result.

    In simple words: A time machine for your project, plus a robot that checks the work before it goes live.

    Deep dive: Short-lived branches, pull requests with review, conventional commits, automated tests and linters, and pipelines that build, scan and deploy in minutes with an easy rollback.

    Expert: Pipelines use caching and parallel jobs, dependency and secret scanning, signed artifacts and environments with approval gates. Releases are blue-green or canary, so a bad version reaches few users and is reverted in one step.

    Git · GitHub Actions · Docker · blue-green deploys

  • Testing and code quality

    Automatic tests run your code against known cases so mistakes show up before visitors see them.

    In simple words: A checklist that runs itself every time you change something.

    Deep dive: Unit tests (Jest, Vitest) check small pieces, integration tests check parts together, and end-to-end tests (Playwright) click through the real app. Linting and type checking (ESLint, TypeScript) catch errors before running.

    Expert: Tests must be deterministic: fake time and network, isolate state, and run in CI on every pull request. Coverage is a hint, not a goal; mutation testing and contract tests show whether the tests would actually notice a bug.

  • Accessibility and performance

    A good site works for everyone and loads quickly, including on slow phones and with screen readers.

    In simple words: Ramps next to the stairs, and a short queue for everybody.

    Deep dive: Use semantic HTML, alt text, keyboard focus and sufficient contrast (WCAG). For speed: compress and size images, lazy-load, cache, and ship less JavaScript. Measure with Lighthouse and Core Web Vitals (LCP, INP, CLS).

    Expert: Performance budgets in CI stop regressions; code splitting, preloading critical resources and server rendering improve first paint; ARIA is a last resort after correct native elements, and real assistive-technology testing beats automated checks alone.

  • Packages and build tools

    Modern sites reuse thousands of ready-made libraries. A package manager such as npm downloads them, and a build tool such as Vite combines them into small files for the browser.

    In simple words: A kitchen delivery: ingredients arrive from suppliers, then get prepared into one neat meal.

    Deep dive: package.json lists what the project needs and a lockfile pins exact versions so every machine builds the same result. Bundlers do tree-shaking to drop unused code and split the output so each page loads only what it needs.

    Expert: Every dependency is a supply-chain risk, so I run npm audit, review new packages, pin versions and keep the tree small. Hashed filenames allow year-long caching, and source maps stay private so debugging does not expose the code.

Networks and Linux, the ground everything stands on

Websites live on servers, and servers talk through networks. If these are built carelessly, the best code in the world can still be stolen, slowed or switched off.

  • Networking

    How computers find and talk to each other: IP addresses, DNS, routers, switches, Wi-Fi, VPNs and firewalls. I design, configure and troubleshoot small and mid-size networks, following the knowledge areas of CompTIA Network+.

    In simple words: Roads, street signs and traffic lights for data, so it always reaches the right address.

    TCP/IP · DNS · DHCP · VLANs · routing · Wireshark

    Deep dive: I reason in layers (OSI and TCP/IP). CIDR subnetting splits address space, VLANs separate traffic on switches, NAT lets private addresses share a public one, and static or dynamic routing chooses paths. TCP opens with a three-way handshake and closes with FIN; UDP skips that for speed (DNS, video). I resolve names with dig, trace paths with traceroute, and inspect traffic with Wireshark and tcpdump.

    Expert: TCP controls congestion with slow start and algorithms such as CUBIC and BBR, while window scaling and selective acknowledgements keep fast links full. QUIC (HTTP/3) moves transport into user space over UDP and avoids head-of-line blocking. BGP exchanges routes between networks, which is why route hijacks matter.

  • Linux servers

    Linux runs most of the internet. I install, secure and maintain Linux servers: users and permissions, SSH access, web servers, automatic updates, logs and backups.

    In simple words: The strong, free operating system behind most websites. I’m the caretaker who keeps it clean, locked and running.

    Ubuntu · Debian · Bash · Nginx · Apache · systemd

    Deep dive: Everything is a file, and access follows owner, group and others (chmod 754). I use sudo sparingly, run services as unprivileged users under systemd with sandboxing options, automate security updates, read logs with journalctl, and script repeatable work in Bash. SSH hardening means key-only login, no root login, rate limiting with fail2ban, and a firewall (UFW or nftables) that denies by default.

    Expert: Kernel-level controls include namespaces, cgroups v2, seccomp-bpf and mandatory access control with AppArmor or SELinux. I tune sysctl for network hardening (SYN cookies, reverse-path filtering), use auditd for tamper-evident records and observe live systems with eBPF tools.

Names and encryption

  • DNS

    The Domain Name System turns names into IP addresses through a chain of servers, and caches answers for a time called the TTL.

    In simple words: The internet’s phone book: you remember a name and it finds the number.

    Deep dive: Records include A and AAAA for addresses, CNAME for aliases, MX for mail, TXT for verification and NS for delegation. Lowering the TTL before a migration makes changes spread quickly.

    Expert: I harden DNS with DNSSEC signing, split-horizon views for internal names, rate limiting against amplification, and checks for dangling records that allow subdomain takeover. SPF, DKIM and DMARC records protect a domain from email spoofing.

    dig · A, AAAA, MX, TXT · DNSSEC · SPF, DKIM, DMARC

Perimeter and access

  • Firewalls and segmentation

    A firewall allows or blocks traffic by rules on address, port and protocol. Segmentation splits a network into zones so a problem in one cannot freely reach the others.

    In simple words: Locked doors between rooms, not just one lock on the front door.

    Deep dive: Default-deny policy, stateful inspection that tracks connections, a DMZ for public servers, VLANs for staff, servers and guests, and logging of every blocked attempt.

    Expert: Rules are written least-privilege per flow, reviewed regularly for shadowed and stale entries, and enforced both at the network edge and on each host with nftables. Management interfaces live on a separate out-of-band network.

    nftables · UFW · VLANs · DMZ · stateful inspection

  • VPN and secure access

    A VPN builds an encrypted tunnel between a device and a private network so traffic is protected on untrusted networks.

    In simple words: A private armoured corridor through a public street.

    Deep dive: I use WireGuard for its small, auditable code and speed, with per-device keys, a minimal allowed-IP list, and SSH keys with multi-factor authentication behind it.

    Expert: Access follows zero-trust ideas: every connection is authenticated and authorised, nothing is trusted because of its network location, and keys are rotated and revoked from one place.

    WireGuard · SSH · bastion host · zero trust

Operations

  • Troubleshooting method

    Network+ teaches a fixed method: identify the problem, form a theory, test it, plan a fix, implement it, verify, and document.

    In simple words: A doctor’s routine: ask, guess, test, treat, check, write it down.

    Deep dive: I work bottom-up through the layers: cable and Wi-Fi first, then IP configuration, then DNS, then the application, using ping, traceroute, ip, ss, dig and curl.

    Expert: When symptoms are intermittent I capture packets with tcpdump and read them in Wireshark: retransmissions point to loss, long gaps to latency, and resets to a firewall or a crashed service.

    ping · traceroute · ip · ss · dig · curl · tcpdump

Linux in depth

  • Filesystem and processes

    Linux organises everything in one tree starting at /. Each running program is a process with an owner, and the system manager (systemd) starts and watches services.

    In simple words: One big building with labelled floors: settings here, user files there, logs over there.

    Deep dive: Settings live in /etc, logs in /var/log and user data in /home. Everyday tools are ps, top, journalctl and systemctl, with find, grep and awk for searching.

    Expert: I read /proc for live kernel data, trace calls with strace, manage resources with cgroups and nice, schedule jobs with systemd timers, and keep services alive with restart policies and watchdogs.

    systemd · journalctl · /proc · cron · strace

  • Containers and isolation

    A container packages an app with everything it needs and runs it in an isolated space on a shared kernel.

    In simple words: A sealed lunch box: the same meal tastes the same wherever you open it.

    Deep dive: Docker images are built from small base images and run as a non-root user, with read-only filesystems and only the ports they need.

    Expert: Isolation rests on namespaces, control groups, capabilities and seccomp profiles. I drop all capabilities, scan images for known vulnerabilities, pin versions by digest, and keep secrets out of image layers.

    Docker · Compose · namespaces · cgroups · seccomp

  • Wireless networks

    Wi-Fi sends data through the air, so it must be encrypted and the access point must be set up carefully.

    In simple words: Talking in a room where anyone can hear: you need a private language.

    Deep dive: Use WPA3 (or WPA2 with AES) with a long passphrase, change default router passwords, keep firmware updated, and put guests and smart devices on a separate network.

    Expert: Enterprise Wi-Fi uses 802.1X with RADIUS and per-user certificates, so there is no shared password to leak. Channel planning, signal strength and roaming settings matter as much as encryption for reliability.

  • DHCP, NAT and ports

    DHCP hands out addresses automatically, NAT lets many devices share one public address, and ports tell a computer which program should receive the data.

    In simple words: A hotel: reception gives each guest a room number, and one street address serves the whole building.

    Deep dive: DHCP leases an IP, subnet mask, gateway and DNS server. NAT translates private to public addresses. Ports such as 22 (SSH), 80 (HTTP), 443 (HTTPS) and 53 (DNS) identify services.

    Expert: Troubleshoot with ip a, ss -tulpn, traceroute and tcpdump. Know that NAT is not a firewall, that UDP has no handshake, and that exposing a port means you own its patching and monitoring.

Ethical hacking: breaking in so others can’t

An ethical hacker has the skills of a criminal and the permission of the owner. I look for weaknesses in websites, servers and networks, then show exactly how to fix them. My knowledge follows CompTIA Security+ for defense and EC-Council CEH for attack techniques.

  • Finding weaknesses

    I test websites and servers for the most common flaws: weak logins, data leaks, broken permissions, injection attacks and misconfigured services, using tools like Nmap, Burp Suite and Wireshark.

    In simple words: I try every door and window of your digital building and tell you which ones were unlocked.

    Deep dive: A test follows the methodology CEH teaches: reconnaissance, scanning and enumeration, gaining access, maintaining access, and clearing tracks, always inside the agreed scope. Web testing follows the OWASP Top 10: broken access control, cryptographic failures, injection, insecure design, misconfiguration, vulnerable components, authentication failures, integrity failures, logging gaps and server-side request forgery. Findings are scored with CVSS and mapped to CWE entries.

    Expert: Manual testing focuses on logic: broken object-level authorisation, race conditions in checkout flows, mass assignment, and chains of low-severity bugs that become critical together. Findings are reproduced, minimised, scored with CVSS v4 and mapped to CWE, then shared through coordinated disclosure.

  • Defending systems

    Strong authentication, encrypted connections, firewalls, updates, least-privilege access and monitoring. Defense is a habit, not a single product.

    In simple words: Good locks, an alarm, and a rule that nobody gets a key they don’t need.

    Deep dive: I design with defense in depth and least privilege around the CIA triad. That means multi-factor authentication, TLS 1.2 or newer everywhere, salted password hashing, network segmentation, patch management, centralized logging, and a rehearsed incident response cycle: prepare, detect, contain, eradicate, recover, learn. The Security+ domains map directly onto this.

    Expert: Controls are mapped to frameworks such as NIST CSF, CIS Controls and ISO 27001. I combine defense in depth with a secure software development lifecycle, software bills of materials (SBOM), dependency pinning, secrets scanning and regular tabletop exercises for incident response.

  • Clear reports

    Each problem is explained in plain words with how serious it is, what could happen, and exactly how to fix it, followed by a retest.

    In simple words: No jargon, just a checklist you can act on.

    Deep dive: Reports follow a fixed structure: executive summary, scope and method, findings ranked by CVSS severity with evidence, business impact, remediation steps, and a retest appendix, so both managers and engineers can use the same document.

    Expert: Findings are scored with CVSS and ordered by real business impact. Each has reproduction steps, evidence, a fix and a retest result, with a short executive summary on top and the technical detail in an appendix.

  • Web vulnerabilities

    Most website break-ins use a handful of well-known mistakes: injection, cross-site scripting (XSS), broken access control, cross-site request forgery (CSRF), and server-side request forgery (SSRF).

    In simple words: The most common mistake is trusting whatever a visitor types, like a shop assistant who does whatever any customer says.

    Deep dive: Fixes are structural: prepared statements against injection, contextual output encoding plus a Content Security Policy against XSS, server-side authorization checks on every request, anti-CSRF tokens and SameSite cookies, and allow-lists for any URL the server fetches.

    Expert: Beyond the basics: DOM-based XSS and Trusted Types, JWT algorithm confusion, insecure deserialization, prototype pollution in JavaScript, SSRF reaching cloud metadata endpoints, and request smuggling between proxies. Each has a structural defence, not a filter.

  • Cryptography

    The mathematics that keeps secrets secret and proves identity: encryption, hashing, digital signatures and certificates.

    In simple words: Locks and wax seals for digital messages. Only the right person can open them, and you can tell if someone tampered.

    Deep dive: AES for bulk data, RSA and elliptic curves for key exchange and signatures, SHA-256 for integrity, Argon2 or bcrypt for passwords (slow on purpose), and TLS with certificate chains (PKI) tying it together.

    Expert: TLS 1.3 removes legacy ciphers and gives forward secrecy through ephemeral Diffie-Hellman, so recorded traffic stays safe even if a key leaks later. I prefer authenticated encryption (AES-GCM, ChaCha20-Poly1305), constant-time comparisons, and never invent my own cryptography. Post-quantum key exchange is already appearing in browsers.

  • Detection and response

    No defense is perfect, so systems must notice trouble quickly: logs, alerts, intrusion detection and a plan for what to do next.

    In simple words: Security cameras and a fire drill. You hope not to need them, and you are glad they exist when you do.

    Deep dive: Central log collection, correlation rules for brute force and privilege changes, network and host intrusion detection (IDS/IPS), file-integrity monitoring, and playbooks that define who contains, who investigates and who communicates.

    Expert: Detection engineering writes rules against attacker behaviour rather than signatures, tests them against replayed attack data and tunes thresholds to keep false positives low. Sigma rules, MITRE ATT&CK coverage maps and honeytokens that alert on touch complement standard monitoring.

Designing against attackers

  • Threat modeling

    Before building, you ask what could go wrong. Threat modeling lists what you protect, who might attack it, and how.

    In simple words: Walking around a house to plan where a burglar would try to get in, before you buy the locks.

    Deep dive: I draw a data-flow diagram, mark trust boundaries, and walk each flow through STRIDE: spoofing, tampering, repudiation, information disclosure, denial of service and elevation of privilege.

    Expert: Each threat is rated by likelihood and impact, mapped to a control, and tracked as a backlog item. Attack trees and MITRE ATT&CK techniques guide detection design, and the model is revisited at every major change.

    STRIDE · data-flow diagrams · attack trees · MITRE ATT&CK

Identity

  • Authentication and passwords

    Authentication proves who you are. Good systems never store passwords; they store a slow one-way hash with a random salt, and add a second factor.

    In simple words: A safe that remembers only the shape of your key, never the key itself.

    Deep dive: Argon2id or bcrypt hashing, unique salts, breached-password checks, rate limiting and lockouts, secure session cookies, and multi-factor authentication with authenticator apps or hardware keys.

    Expert: Passkeys (WebAuthn) remove passwords entirely using public-key cryptography bound to the site, which defeats phishing. Tokens are short-lived, rotated, bound to the client and revocable, and algorithm choices are pinned to prevent downgrade tricks.

    Argon2 · bcrypt · TOTP · WebAuthn · OAuth2

When things go wrong

Known weakness families

  • Vulnerability management

    Finding every weakness is impossible, so the work is to find the important ones first and fix them quickly.

    In simple words: A garage check-up: fix the brakes before the paint.

    Deep dive: Keep an asset inventory, scan regularly, rank findings with CVSS plus context such as internet exposure, then patch, mitigate or accept the risk with a written owner and date.

    Expert: Use EPSS and the known-exploited list to rank by real-world likelihood, track mean time to remediate, and tie findings to owners in a ticket system so nothing is only a report.

  • Mobile and AI security

    Phones and AI tools add new places where data can leak or be tricked.

    In simple words: Treat your phone like a wallet and an AI like a helpful stranger: do not hand over secrets.

    Deep dive: Mobile: update the OS, use a screen lock and biometrics, install apps only from official stores, review permissions. AI: never paste passwords or private data, and verify answers.

    Expert: App security follows the OWASP MASVS (secure storage, certificate pinning, tamper checks). For LLM features, prompt injection, data leakage and over-privileged tools are the main risks; defend with input and output filtering, least-privilege tool access and human approval for sensitive actions.

I only ever test systems I own or have written permission to test.

Advanced engineering: cloud, trust and scale

  • Containers and Kubernetes

    Kubernetes runs many containers across many machines and keeps them healthy, updated and reachable.

    In simple words: A manager for a fleet of identical shipping containers: if one breaks, a new one is put in its place automatically.

    Deep dive: You declare the desired state in YAML (Deployments, Services, Ingress, ConfigMaps, Secrets). Controllers continuously reconcile reality with it. Rolling updates, readiness probes and resource requests and limits keep releases safe and nodes fair.

    Expert: Production hardening: namespaces with RBAC, NetworkPolicies default-deny, Pod Security Standards (non-root, read-only filesystem, dropped capabilities), signed and scanned images, secrets from an external vault, and an admission controller enforcing policy before anything runs.

  • Zero trust and identity

    Never trust a request just because it comes from inside the network. Verify who it is, what device it is, and whether it looks normal.

    In simple words: Like a building where every door checks your badge, not just the front entrance.

    Deep dive: Strong identity (SSO, MFA, passkeys), device posture checks, short-lived tokens (OIDC and OAuth 2.0 scopes), least privilege and micro-segmentation, with every decision logged.

    Expert: Continuous evaluation: a policy engine scores session risk and can step up authentication or revoke access mid-session. Service-to-service traffic uses mutual TLS with workload identities (for example SPIFFE) so a stolen network position is worthless.

  • Scaling and performance

    Fast sites avoid doing the same work twice: files come from a nearby CDN, traffic is spread across servers, and popular data is cached.

    In simple words: Many checkout lanes instead of one, and the popular items kept right next to the cashier.

    Deep dive: Layer 4 and 7 load balancing with health checks, horizontal scaling behind stateless services, HTTP caching headers, Redis for hot data, database indexes and read replicas, and queues to move slow jobs out of the request.

    Expert: Capacity work is measured, not guessed: load tests find the knee of the latency curve, p95 and p99 latency matter more than averages, caches need an invalidation strategy and stampede protection, and sharding or partitioning is the last step because it is hard to undo.

  • Observability and delivery

    Logs, metrics and traces show what a system is doing, and an automatic pipeline tests and ships each change safely.

    In simple words: A car dashboard plus a factory line that checks every part before it leaves.

    Deep dive: The three pillars: structured logs, metrics (rate, errors, duration) and distributed traces with correlation IDs. CI/CD runs tests, linting, dependency and secret scanning, builds an image, and deploys with canary or blue-green releases.

    Expert: Service-level objectives with error budgets decide when to ship versus stabilise. Infrastructure is code (Terraform, GitOps), builds are reproducible with signed artifacts and an SBOM, and every alert links to a runbook so on-call response is a procedure, not improvisation.

  • Queues and background jobs

    Some work is too slow to do while a visitor waits. The app drops it into a queue and a separate worker picks it up, so the page answers at once.

    In simple words: A restaurant ticket rail: the waiter hangs the order and returns to the guests while the cook works through the tickets.

    Deep dive: Queues such as RabbitMQ, Redis or SQS decouple the sender from the receiver. Jobs are acknowledged only after success, failed ones retry with exponential back-off, and jobs that keep failing move to a dead-letter queue for inspection.

    Expert: Delivery is at-least-once, so every worker must be idempotent: running the same job twice must give the same result. I size consumers from queue depth, use partition keys to keep related events in order, and alert on message age, not only on count.

  • Cloud service models

    The cloud comes in layers. IaaS rents raw machines, PaaS rents a ready platform, serverless runs single functions, and SaaS is a finished app you just use.

    In simple words: Pizza: make it at home, order a kit, get it delivered, or eat at the restaurant.

    Deep dive: The shared responsibility model says the provider secures the hardware and you secure your data, identities and configuration. Costs follow usage, so I add budgets and alerts, and tag every resource with an owner.

    Expert: Most cloud breaches are misconfiguration: open storage buckets, over-broad IAM roles and leaked keys. I apply least privilege, short-lived credentials, private networks by default and continuous posture scanning, and design for multiple zones to survive an outage.

Expert tracks: routing, hardening and forensics

  • Routing at internet scale

    Inside a company, routers learn paths with protocols like OSPF. Between companies and countries, the internet uses BGP.

    In simple words: OSPF is the road map of one city; BGP is the agreement between countries about which borders to cross.

    Deep dive: OSPF builds a link-state map and runs shortest-path (Dijkstra). BGP exchanges prefixes between autonomous systems and chooses by policy: local preference, AS-path length, then MED. IPv6 replaces scarce IPv4 addresses with 128-bit ones and removes the need for NAT.

    Expert: Route hijacks and leaks happen when a network announces prefixes it does not own. Defences: RPKI route-origin validation, prefix filters, max-prefix limits and BGP monitoring. Modern transport adds QUIC and HTTP/3 over UDP to avoid head-of-line blocking and speed up handshakes.

  • Private tunnels and VPNs

    A VPN wraps traffic in an encrypted tunnel so it can cross an untrusted network safely.

    In simple words: A sealed armoured truck driving through a public road.

    Deep dive: IPsec secures whole networks (site to site); WireGuard is a small modern protocol with fast handshakes and a tiny code base; TLS-based VPNs suit remote users. Split tunnelling decides which traffic goes inside.

    Expert: Design choices matter more than the product: key rotation, certificate or key-based device identity, DNS leak prevention, MTU tuning to avoid silent fragmentation, and logging at the gateway for detection.

  • Linux hardening

    Reduce what an attacker can reach and limit what they can do if they get in.

    In simple words: Lock unused doors, give each person only their own key, and keep the spare copy somewhere safe.

    Deep dive: Close unused ports and services, key-only SSH with root login disabled, automatic security updates, a default-deny firewall (nftables or ufw), fail2ban for repeated failures, and auditing with auditd.

    Expert: Mandatory access control (AppArmor or SELinux), systemd sandboxing (NoNewPrivileges, ProtectSystem, private temp), kernel hardening through sysctl, immutable and encrypted backups, and configuration checked continuously against the CIS Benchmarks.

  • Digital forensics

    After an incident, forensics reconstructs the story from traces on computers and networks.

    In simple words: Detective work: photograph the scene first, then investigate a copy, never the original.

    Deep dive: Collect volatile data first (memory, connections), image disks with write blockers, record SHA-256 hashes, and keep a chain of custody. Build a timeline from logs, file times and browser or system artifacts.

    Expert: Analysis correlates host, network and cloud logs, checks persistence points (scheduled tasks, services, startup entries) and hunts for indicators of compromise. Findings map to MITRE ATT&CK so defenders can fix detection gaps, and the report separates evidence from assumptions.

  • Packet analysis

    When something is wrong on the network, packet analysis shows exactly what was sent, in order, instead of guessing. Tools such as Wireshark and tcpdump capture the traffic.

    In simple words: A court stenographer for the network: every word spoken is written down and can be replayed.

    Deep dive: I capture on the right interface, narrow it with capture and display filters (host, port, protocol), then follow one TCP stream. Retransmissions, resets and long gaps between request and reply show whether the fault is the network, the server or the app.

    Expert: I read sequence numbers, window sizes and round-trip times to tell packet loss from congestion, decrypt TLS in a lab using session keys, and compare captures taken at both ends. Captures contain real data, so I store and delete them under the same rules as passwords.

  • Logging and auditing

    Linux records logins, commands and errors in logs. Reading them tells you who did what and when, and is how most attacks are noticed.

    In simple words: A building’s security camera and visitor book, kept where the thief cannot reach.

    Deep dive: journalctl reads systemd logs, /var/log/auth.log shows logins and sudo use, and auditd records file and system-call activity. Logs rotate so disks do not fill, and are forwarded off the machine.

    Expert: An attacker with root deletes local logs first, so I ship them in real time to a write-only collector, synchronise clocks with NTP so timelines line up, write alert rules for failed-login bursts and new admin accounts, and keep retention long enough for forensics.

Systems and data: databases, APIs and the cloud

  • Databases and data design

    A database stores data safely and finds it fast. SQL databases use tables and relations; NoSQL stores fit other shapes like documents or key-value pairs.

    In simple words: A well-organised archive with an index at the front, instead of a heap of papers.

    Deep dive: Normalised schemas avoid duplicated data; indexes speed up reads; transactions follow ACID (atomic, consistent, isolated, durable); replicas give read scaling and failover; backups with tested restores protect against mistakes.

    Expert: Query plans (EXPLAIN) show where time goes. Isolation levels trade correctness for concurrency, connection pooling protects the server, migrations must be backward compatible for zero-downtime deploys, and the CAP theorem reminds you that a partition forces a choice between consistency and availability.

  • API and web security in depth

    An API is a front door for programs, so it needs identity, limits and validation on every request.

    In simple words: A receptionist who checks your badge, your appointment and how many times you visited today.

    Deep dive: Authenticate with OAuth 2.0 and OpenID Connect, authorise on the server for each object, validate all input, set rate limits, restrict CORS, send security headers (CSP, HSTS), and keep secrets out of code.

    Expert: The OWASP API Security Top 10 starts with broken object-level authorisation, so every lookup by ID must check ownership. Use short-lived access tokens with rotating refresh tokens, verify JWT signature, audience and expiry strictly, log security events, and test with automated scanners plus manual review.

  • Cloud and infrastructure as code

    The cloud rents computing power on demand. Infrastructure as code describes it in files that can be reviewed and repeated.

    In simple words: A recipe card for your whole server room, so you can rebuild it exactly, any time.

    Deep dive: Terraform or similar tools plan and apply changes; state tracks what exists; modules reuse patterns; separate environments (dev, staging, production) use the same code with different values.

    Expert: Remote encrypted state with locking, least-privilege IAM roles instead of long-lived keys, policy-as-code checks before apply, drift detection, tagging for cost control, multi-AZ design for resilience, and regular restore and failover drills.

  • System design thinking

    Good design starts with questions: how many users, how fast, how reliable, and what happens when a part fails.

    In simple words: Planning a bridge for the heaviest traffic day, not an average one.

    Deep dive: Break the system into services with clear contracts, use queues to absorb spikes, make retries safe with idempotency keys, add timeouts and circuit breakers, and measure with SLOs.

    Expert: Trade-offs are explicit: consistency versus latency, cost versus redundancy, simplicity versus flexibility. Back-of-envelope capacity estimates, failure-mode analysis and written decision records keep a design honest as it grows.

  • Backups and disaster recovery

    Hardware fails, people make mistakes and attackers encrypt data. A backup is only useful if it is separate, recent and proven to restore.

    In simple words: A spare key kept at a friend’s house, which you have actually tried in the lock.

    Deep dive: The 3-2-1 rule: three copies, on two kinds of storage, one off-site. I schedule automatic backups, encrypt them, and run restore tests on a calendar, because an untested backup is only a hope.

    Expert: I set RPO (how much data may be lost) and RTO (how long recovery may take) with the business, then pick snapshots, replication or point-in-time recovery to meet them. Immutable or offline copies defeat ransomware that deletes backups, and the runbook is rehearsed in drills.

  • Caching strategies

    A cache stores the result of expensive work so the next request is answered instantly. It can live in the browser, at a CDN, or in memory with Redis.

    In simple words: A notebook of answers you already worked out, so you do not redo the sum every time.

    Deep dive: Cache-aside loads on a miss and stores the result with a TTL. Writes either update or invalidate the entry. Headers like Cache-Control and ETag let browsers and CDNs reuse responses safely.

    Expert: The hard part is invalidation. I prevent cache stampedes with request coalescing and jittered TTLs, never cache personalised or private responses on shared layers, and watch hit ratio and eviction rate to size memory.

WordPress: build it, speed it up and protect it

WordPress runs a large share of the web, from personal blogs to big online stores. I build custom themes, plugins and blocks, connect it to modern front-ends, and harden it so it stays fast and safe.

Simple explanationTechnical detailDeep diveExpert level

How WordPress works

  • What WordPress is

    WordPress is a free, open-source content management system written in PHP. You manage pages, posts, images and users from a dashboard, and the site is built from a theme for looks and plugins for features.

    In simple words: A shop where the shelves are easy to rearrange: you change the stock from a back office, and the window dressing is a separate choice.

    Deep dive: Core handles content, users, media, routing and the admin. Themes control presentation; plugins add behaviour through hooks. Content lives in MySQL or MariaDB, uploads on disk, and the same install can serve a blog, a company site or a store with WooCommerce.

    Expert: I treat WordPress as an application framework: a mature plugin API, the REST API, custom post types and a block editor on top of React. The trade-off is a very large attack surface and a global-state, hook-driven design, so structure and discipline matter more than in a greenfield framework.

    WordPress · PHP · MySQL · Gutenberg

  • The request lifecycle and the Loop

    Every URL goes to index.php, which loads WordPress. Core parses the address, builds a database query, picks a template and prints the result. The part of a template that prints posts is called the Loop.

    In simple words: A waiter takes your order, the kitchen finds the dish in the pantry, and the plate is arranged the same way every time.

    Deep dive: wp-load.php reads wp-config.php, connects to the database, loads active plugins and the theme, then the main query runs from the rewrite rules. The template calls have_posts and the_post to loop over the results, and the_title or the_content to print them.

    Expert: Hooks fire in a fixed order (plugins_loaded, init, wp_loaded, template_redirect, wp_head, wp_footer), so code placed on the wrong hook runs too early or too late. I use pre_get_posts to change the main query instead of running a second one, and WP_Query with no_found_rows or fields set to ids when I only need a list.

    index.php · WP_Query · the Loop · rewrite rules

  • Files and the database

    A WordPress install is a handful of folders plus a database. Your own work lives in wp-content, and nearly everything else is core that updates itself.

    In simple words: Core is the building. Themes, plugins and uploads are the furniture you bring in; the database is the filing cabinet.

    Deep dive: wp-config.php holds the database login and secret keys. The database has tables for posts, post meta, users, comments, terms and options. Posts, pages, menu items and products are all rows in wp_posts, with extra fields in wp_postmeta.

    Expert: wp_options rows marked autoload are read on every request, so a plugin that stores big values there slows every page. The meta table is a key-value store with no good index on values, which is why heavy meta queries get slow; I move such data to a custom table with proper indexes or to a taxonomy.

    wp-config.php · wp_posts · wp_postmeta · wp_options

Building with WordPress

  • Themes and block themes

    A theme decides how the site looks. Classic themes are PHP template files; block themes describe the whole site, header and footer included, in HTML templates and one theme.json file.

    In simple words: The paint, floor plan and signs of the shop. You can repaint without moving a single product.

    Deep dive: Template hierarchy picks the most specific file, such as single-product.php before single.php before index.php. A child theme overrides a parent safely so updates do not erase changes. In a block theme, theme.json sets colors, fonts, spacing and layout once for the editor and the front end.

    Expert: I build block themes with theme.json design tokens, patterns and template parts, load fonts locally, and ship no jQuery. Styles are enqueued only where used, critical CSS is small, and blocks get style variations rather than custom CSS overrides so editors keep control without breaking the design.

    theme.json · template hierarchy · child themes · patterns

  • Plugins and hooks

    A plugin is a PHP file that adds a feature. It plugs into WordPress through hooks: actions run your code at a moment, filters change a value before it is used.

    In simple words: Sockets in a wall. The house stays the same, and you plug in whatever device you need.

    Deep dive: add_action attaches a function to an event such as init or save_post; add_filter changes data such as the_content. Plugins are activated per site, can register settings, shortcodes, post types and admin pages, and must clean up on uninstall.

    Expert: Good plugins use a prefix or namespace, load code only where needed, keep settings in one option, and use the Settings API. I write them with Composer autoloading, unit tests with the WordPress test suite, and priorities set deliberately because two callbacks on the same hook run in priority order.

    add_action · add_filter · Settings API · shortcodes

  • Content model: posts, types and taxonomies

    Posts and pages are only two kinds of content. Custom post types add your own, such as Project or Course, and taxonomies group them with categories and tags.

    In simple words: Different kinds of cards in a card file, each with its own labelled slots.

    Deep dive: register_post_type creates the type and register_taxonomy the groupings; register_meta and the REST API expose custom fields. Advanced Custom Fields or native meta boxes give editors tidy forms for those fields.

    Expert: I model content first: which fields belong in post meta, which in taxonomies for filtering, and which need a custom table. Slugs, rewrite rules and capabilities are defined with the type, and flush_rewrite_rules runs once on activation, never on every request.

    Custom post types · taxonomies · ACF · meta

  • Gutenberg blocks

    The block editor builds pages from blocks: paragraph, image, columns, or your own. Custom blocks are written with JavaScript and React, so front-end skills carry straight over.

    In simple words: LEGO bricks for page content, and I can mold brand-new brick shapes for you.

    Deep dive: A block has a block.json file describing its name, attributes and assets, an edit component for the editor and a save function or PHP render for the front end. The wp-scripts package builds it with webpack.

    Expert: I prefer dynamic blocks rendered in PHP when content must stay fresh or secure, and static blocks when markup should be stored. Attributes are validated by schema, block deprecations keep old content working after changes, and InnerBlocks and block bindings let editors compose without code.

    block.json · React · @wordpress/scripts · InnerBlocks

  • REST API and headless WordPress

    Every WordPress site has a REST API at /wp-json. A headless setup uses WordPress only as the content back office, while a separate front-end such as React or Next.js draws the pages.

    In simple words: The kitchen stays, but you can serve the food in any restaurant you like.

    Deep dive: Endpoints such as /wp-json/wp/v2/posts return JSON. Custom routes are added with register_rest_route and a permission callback. Public data is open, private data needs authentication with application passwords or JWT.

    Expert: Headless trades simplicity for freedom: previews, forms, SEO metadata and caching must be rebuilt in the front-end. I use incremental static regeneration with webhooks on publish, WPGraphQL when the front-end needs exact fields, and lock the admin behind a separate domain and rate limits.

    REST API · WPGraphQL · Next.js · application passwords

  • WooCommerce and online stores

    WooCommerce turns WordPress into an online shop: products, variations, cart, checkout, taxes, shipping and orders, with hundreds of payment and delivery extensions.

    In simple words: A cash register, shelves and a delivery desk added to your website.

    Deep dive: Products are a post type, orders are custom entities, and payment gateways process the money. Pages for cart and checkout are blocks, and emails, stock and taxes are configured in the admin. Card details never touch your server when a hosted gateway is used.

    Expert: High-order stores need HPOS (high-performance order storage), object caching, background queues through Action Scheduler and carefully chosen extensions, since each one adds queries at checkout. I keep checkout pages uncached, test every gateway in sandbox, verify webhook signatures and keep logs of failed payments.

    WooCommerce · gateways · HPOS · Action Scheduler

Running and protecting it

  • Performance

    A slow site loses visitors and search ranking. WordPress is fast when most requests never reach PHP, thanks to caching, a CDN, optimised images and a lean set of plugins.

    In simple words: Keep popular answers on the counter instead of walking to the storeroom each time.

    Deep dive: Page caching stores finished HTML. Object caching with Redis keeps database results in memory. Images are resized and served as WebP or AVIF, scripts are deferred, and unused plugins are removed. PHP 8 with OPcache is much faster than old versions.

    Expert: I measure first with Query Monitor, slow query logs and Core Web Vitals, then fix the biggest cost. Typical wins: remove autoloaded junk, add missing indexes, replace heavy page builders, cache fragments, move cron to a real system cron, and keep TTFB low by serving cached pages from the edge.

    Redis · OPcache · CDN · Query Monitor · Core Web Vitals

  • Security hardening

    WordPress is a popular target, mostly through outdated plugins, weak passwords and bad hosting. Protecting it means layers: server, core, plugins, accounts and monitoring.

    In simple words: A shop with a strong door, alarm, camera, a short key list and a guard who checks the news for new burglar tricks.

    Deep dive: Keep core, themes and plugins updated and delete what you do not use. Use strong unique passwords with two-factor login, limit login attempts, disable file editing in the dashboard, use HTTPS everywhere, and set file permissions so uploads cannot run code.

    Expert: Beyond the basics: a WAF at the edge, DISALLOW_FILE_EDIT and DISALLOW_FILE_MODS in production, no PHP execution in uploads, XML-RPC off unless needed, unique salts, least-privilege database user, user enumeration blocked, security headers and a CSP, file-integrity checks with WP-CLI checksums, and alerts on new admin users.

    WAF · 2FA · file permissions · wp-config · CSP

  • Secure plugin and theme code

    Most WordPress vulnerabilities come from custom code that trusts input. The rule is simple: check who is asking, check intent, clean what comes in and escape what goes out.

    In simple words: Check the ID, check the ticket, wash the vegetables when they arrive, and wrap the plate before it leaves.

    Deep dive: current_user_can checks permission, nonces check intent and defeat CSRF, sanitize_text_field and similar functions clean input, and esc_html, esc_attr and esc_url escape output. Database queries use wpdb prepare so input can never become SQL.

    Expert: Every AJAX and REST handler needs a capability check, not only a nonce, because nonces prove intent but not authority. I validate with allow-lists, escape late at the point of output, avoid unserialize on user data, restrict uploads by real MIME type, and run PHPCS with the WordPress security rules in CI.

    nonces · capabilities · esc_html · wpdb prepare · PHPCS

  • Users, roles and capabilities

    WordPress has five built-in roles: Administrator, Editor, Author, Contributor and Subscriber. Each role is a bundle of capabilities such as edit_posts or manage_options.

    In simple words: Staff badges: the cleaner, the cashier and the manager open different doors.

    Deep dive: Give people the lowest role that lets them work. Custom roles are created with add_role, and checks are written against capabilities, never role names. Shared admin accounts are replaced by named accounts.

    Expert: On larger sites I define custom capabilities per post type with map_meta_cap, so Editors of one section cannot touch another. Admin accounts get hardware-key 2FA, sessions are time-limited, and a log records logins, role changes and plugin installs for audit.

    roles · capabilities · map_meta_cap · audit log

  • WP-CLI and deployment

    WP-CLI controls WordPress from the terminal. With Git, Composer and a staging site, changes are tested first and shipped the same way every time.

    In simple words: A remote control for the site, plus a rehearsal stage before the live show.

    Deep dive: Commands like wp plugin update and wp db export replace clicking. Code lives in Git, secrets in environment variables, and uploads and the database are synced between staging and production with search-replace for URLs.

    Expert: I use Composer to pin plugin versions (Bedrock style), build assets in CI, deploy by atomic symlink swap, run wp cache flush and rewrite flush as steps, and keep zero-downtime rollbacks. Database changes ship as migrations or WP-CLI scripts, never as manual edits on production.

    WP-CLI · Composer · Git · staging · CI/CD

  • Multisite, backups and maintenance

    Multisite runs many sites from one install. Whatever the setup, a site needs automatic backups, update routines and monitoring, because maintenance is what keeps it alive.

    In simple words: A building manager: one set of pipes for many flats, and regular inspections so nothing floods.

    Deep dive: Multisite shares core, plugins and users while each site has its own tables. Backups follow the 3-2-1 rule: files and database, off-site, restore tested. Uptime monitoring and log review catch trouble early.

    Expert: I schedule daily database and weekly full backups, keep immutable off-site copies, and rehearse a restore. Updates go staging first with visual regression tests, automatic updates for minor and security releases, and a runbook defines who rolls back, who communicates and how fast the site must return (RTO).

    Multisite · 3-2-1 backups · monitoring · runbooks

Core ideas, in motion

Four lessons that explain how the web works and how to keep it safe. Each animation loops so you can watch it as many times as you need.

What happens when you open a website

  • Web request

    Your browser asks a directory called DNS for the server's address, then sends a request to that server, and the server answers with the page.

    In simple words: Like looking up a shop's address in a phone book, walking there, and asking for what you want.

    Deep dive: DNS returns an IP address, the browser opens a TCP connection, upgrades it with TLS, sends an HTTP GET, and renders the HTML, CSS and JavaScript that come back. Caches at every step make repeat visits fast.

    Expert: Modern browsers reuse connections and can use HTTP/3 over QUIC, which stops one slow packet from blocking the rest. DNS answers are cached for their TTL, and the DevTools Network waterfall shows where the time really went.

Why the padlock matters (HTTPS)

  • HTTPS

    HTTPS scrambles everything between you and the website, so anyone listening on the way sees only noise.

    In simple words: Like sending a letter in a locked box that only the receiver has the key to.

    Deep dive: TLS authenticates the server with a certificate, agrees a shared session key with an ephemeral key exchange, then encrypts traffic with a fast symmetric cipher such as AES-GCM or ChaCha20.

    Expert: TLS 1.3 finishes its handshake in one round trip and gives forward secrecy, so a stolen key cannot unlock old recordings. The certificate must chain to a trusted root, and HSTS tells browsers never to try plain HTTP again.

Saving your work with Git

  • Git

    Git records every change as a commit. Branches let you try an idea safely, and a merge brings it back when it works.

    In simple words: Like saving numbered versions of a document, and drafting a risky chapter on a separate copy first.

    Deep dive: Commits are immutable snapshots identified by hashes. Feature branches, pull requests and code review keep main deployable, and rebase or squash keeps history readable.

    Expert: Commits are immutable snapshots named by a hash and linked into a graph. Rebase rewrites history and merge preserves it; never rewrite a branch others use. git bisect finds the exact commit that introduced a bug by halving the search.

Who can do what: Linux permissions

  • Permissions

    Every file has three sets of permissions: for its owner, for a group, and for everyone else. Each set can allow reading, writing and running.

    In simple words: Like keys to a house: the owner can do everything, family can enter, strangers can only look from outside.

    Deep dive: Permissions are bits: read 4, write 2, execute 1, so 755 means rwx for the owner and r-x for the rest. I apply least privilege, use groups instead of sharing accounts, and audit with find and getfacl.

    Expert: Beyond rwx there are setuid, setgid and the sticky bit, umask sets the defaults for new files, and ACLs add per-user rules. Mandatory access control such as SELinux or AppArmor still limits a program that runs as root.

  • DNS records and email trust

    DNS holds more than addresses: it also says which servers handle email and which ones may send it.

    In simple words: The phone book also lists who is allowed to sign letters in your name.

    Deep dive: A and AAAA point to addresses, CNAME aliases a name, MX routes mail, TXT carries SPF, DKIM and DMARC policies, and TTL controls caching.

    Expert: Roll out DMARC gradually (none, quarantine, reject) while reading aggregate reports, add DNSSEC where supported, and keep a short TTL before migrations so changes spread quickly.
